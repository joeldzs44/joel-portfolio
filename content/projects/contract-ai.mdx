<Problem label="01 / The problem" title="Enterprise contracts are long, and the important parts hide.">

Procurement teams manage thousands of contracts. Finding a specific clause, a renewal date or a liability cap meant reading documents end to end.

The module had to work for many clients at once, process bulk uploads without slowing anyone down, and meet enterprise security expectations — clients were trusting it with their most sensitive documents.

I architected the module and built it as a set of services, each responsible for one task, so it could grow with adoption instead of being rebuilt for it.

</Problem>

<Approach label="02 / System design" title="One service per task, one queue in front." intro="Microservices on Azure Kubernetes, fed by Kafka, observed end to end.">

<Stage step="01 / Intake" title="Documents and bulk uploads">
Contracts arrive one at a time or in large batches, and every job goes onto a Kafka queue first.
</Stage>

<Stage step="02 / Clauses" title="Clause identification">
A transformer model fine-tuned on enterprise proprietary data classifies contract clauses quickly and predictably.
</Stage>

<Stage step="03 / Entities" title="Named entity recognition">
NER pulls specific data points — parties, dates, values — out of each contract into structured fields.
</Stage>

<Stage step="04 / Assistant" title="Contract Q&A with RAG">
The Q&A assistant is a RAG pipeline built with LangChain: contracts are chunked and embedded into Qdrant, and each answer is grounded in the retrieved passages, behind the platform's guardrails.
</Stage>

<Decision title="Scale each task on its own.">
Every capability ran as its own FastAPI service on Azure Kubernetes with horizontal scaling. A large bulk upload scaled the services doing that work without affecting anyone using the assistant.
</Decision>

<Decision title="Security and visibility were built in from the start.">
RBAC, PII masking and prompt-injection defences protected client data; SonarCloud and GitHub Advanced Security checked every change. New Relic and Langfuse showed how each service and model call behaved in production.
</Decision>

</Approach>

<Reflection label="03 / Evaluation" title="Adoption was the real test.">

The module is used by more than 20 enterprise clients. The design decisions that mattered most were the unglamorous ones: a queue in front of everything, services that scale independently, and guardrails clients could audit.

Using a fine-tuned transformer for clause identification, rather than an LLM for everything, kept the highest-volume task fast, cheap and consistent.

</Reflection>

<Takeaways>

<Takeaway label="04 / What I’d keep" title="Pick the right model for each task.">
A fine-tuned transformer for high-volume classification, and RAG with an LLM only where open-ended questions needed it, gave the best balance of cost, speed and accuracy.
</Takeaway>

<Takeaway label="05 / What comes next" title="Deeper answers across many contracts.">
The natural next step is questions that span a client's whole contract portfolio, with the same security model and observability.
</Takeaway>

</Takeaways>
